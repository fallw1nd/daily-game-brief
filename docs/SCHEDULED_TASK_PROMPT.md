# Scheduled Task Editorial Contract

Production uses one active long-lived ChatGPT editorial task: Daily at 10:20, `Asia/Shanghai`. The former PM task is disabled. Daily closes evidence at 10:10 and is planned for public release at 12:00. The first production Daily, `2026-08-31-daily`, uses `(2026-08-30 17:00, 2026-08-31 10:10]`; later Daily editions use `(previous day 10:10, current day 10:10]`.

The task has three bounded checks in order: current Canonical editorial work first, then current Daily liveness wake, then at most one published English repair. English never blocks or changes verified Simplified Chinese Canonical facts, and historical locale backlog must never consume the only independent wake opportunity for the current Daily.

## 1. Resolve Canonical work and current Daily liveness
1. On `automation/state`, select the oldest already-due Daily edition with `packet.status:"ready"`, publication not committed, and `editorial.status` `pending` or `invalid`. `pending` starts a decision; `invalid` repairs one using durable `validationErrors` and `submissionSha`. `submitted`/`valid` belong to GitHub's publication lane and `timed_out` to its SLA lane; never select or re-edit them. Never skip Canonical backlog or derive its identity from runner time.
2. For eligible work, read `automation/status/<edition-id>.json`, then read the packet by its Git blob SHA. Copy it unchanged to `packetBlobSha`. Require packet schema v3, `mode:"chatgpt-handoff"`, editorial input v2, exact edition/period/plannedAt/window, cutoff coverage, and post-cutoff finalization.
3. After packet preflight, read current `main` `AGENTS.md`, this contract, manifest/latest, title registry, and the edition archive when present. `main` is authoritative even when durable state lags. A normal Canonical already present is not re-edited; only an absent Canonical or `[自动事实清单]` may enter the Canonical decision path.
4. If no Canonical work exists, derive the immediate next missing Daily from current `main` before English repair. If that edition's 10:10 cutoff has passed and `automation/state` has no acknowledged `packet.status:"ready"` for that exact edition, create/reuse `automation/editorial/<edition-id>` from current `main`, commit only `automation/wake/<edition-id>.json` with reason `packet_missing_at_handoff`, then stop. Do not wake when that exact edition already has a ready packet or is in GitHub-owned `submitted`, `valid`, `timed_out`, committed, or deployed progress. Never infer edition identity from Actions timing.
5. Only when no Canonical decision and no current missing-packet wake is required may the task continue to one English repair.

## 2. Produce and submit Canonical
- Return exactly one `include`, `exclude`, or `needs_review` for every packet package/tracking item; add nothing outside the packet. Use only opened evidence. `official` needs opened primary evidence; `multi_source_verified` needs two independent reliable sources. Never invent a `requires_subject_identity` subject. Daily uses `upcomingMode:"replace"`.
- Follow live `AGENTS.md` for Chinese names, mainland terminology, sources, time boundaries, copy, and uncertainty. Narrow naming lookups cannot change facts. Every include needs a complete language-neutral `sharedFactFrame`; do not invent issue numbers, final `entryId`, or digests.
- For every normal Daily submission, attempt complete `locales.en` by default. English is nonblocking, but omission is exceptional. English entries/upcoming must fully match the submitted Canonical order and stay inside the same evidence/sharedFactFrame. Never use Chinese body copy as fallback or add new facts. If complete English cannot safely be produced, omit `locales.en`; GitHub records an unavailable state for repair.
- Create/reuse `automation/editorial/<edition-id>` from current `main` and commit only `automation/inbox/<edition-id>.json`. After that commit succeeds, do not poll Actions; continue only to the one-item English repair check when no current Daily wake was required.

## 3. Repair at most one English backlog item
1. Consider published Daily editions from `2026-08-31-daily` onward whose current English status is unavailable with `editorial-overlay-missing` or `editorial-overlay-invalid`; choose the oldest. Ignore editions with a valid Overlay.
2. Read the current Canonical archive. Final Canonical `entryId` and order are authoritative even when a preserved formal entry no longer has an eventKey in the newest revision.
3. Draft schema v1 `locale:"en"` repair data for the exact edition. Each English entry uses final Canonical `entryId`; entries and upcoming must cover current Canonical exactly once in order. Supply only presentation fields: archiveTitle, headline, summary, verification, timeNote, needed labels, and optional sourceReport. Do not calculate digests or include fact/time status, source URLs, platforms, dates, tracking, issue number, or other Canonical authority fields.
4. Restate only existing Canonical/accepted evidence. Do not rediscover news or introduce later facts. Create/reuse `automation/locale/en/<edition-id>` from current `main` and commit only `automation/locale-inbox/<edition-id>.json`. Trusted GitHub code validates against Canonical IDs/factsDigest, hash-guards archive/latest/manifest, updates only English availability/Overlay, deploys Pages when changed, and closes the degraded-English incident. Then stop.

Do not inspect or poll Actions, create/delete workflows, edit `automation/state`, publish Canonical directly, advance editions, or mutate the long-lived task. GitHub Actions owns collection recovery, validation, trusted publication, deployment, state acknowledgement, and incidents. A single Canonical or locale failure must never pause, disable, rename, reschedule, or otherwise mutate the active Daily task.
