# Scheduled Task Editorial Contract

Production uses one active long-lived ChatGPT editorial task with two exact Daily invocations at 10:20 and 11:20, `Asia/Shanghai`; the former PM task is disabled. Daily closes evidence at 10:10, GitHub's degraded fallback deadline is 11:40, and public release remains planned for 12:00. The first production Daily, `2026-08-31-daily`, uses `(2026-08-30 17:00, 2026-08-31 10:10]`; later Daily editions use `(previous day 10:10, current day 10:10]`.

Both invocations use the same idempotent contract. The task has three bounded checks in order: current Canonical editorial work first, then current Daily liveness wake, then at most one published English repair. There is still only one long-lived ChatGPT task.

## 1. Canonical and liveness
1. On `automation/state`, select the oldest already-due Daily edition with `packet.status:"ready"`, publication uncommitted, and editorial `pending` or `invalid`. `pending` starts a decision; `invalid` repairs one using durable `validationErrors` and `submissionSha`. `submitted`/`valid` belong to GitHub's publication lane and `timed_out` to its degraded fallback lane; never select or re-edit them. Never skip Canonical backlog or derive its identity from runner time.
2. For eligible work, read `automation/status/<edition-id>.json`, then read the packet by its Git blob SHA. Copy it unchanged to `packetBlobSha`. Require packet v3, `mode:"chatgpt-handoff"`, editorial input v2, exact edition/period/plannedAt/window, cutoff coverage, and post-cutoff finalization.
3. Read current `main` `AGENTS.md`, this contract, manifest/latest, title registry, and the edition archive if present. `main` is authoritative. Do not re-edit normal Canonical; only absent Canonical or `[自动事实清单]` enters the decision path.
4. If no Canonical work exists, derive the immediate next missing Daily from current `main` before English repair. After its 10:10 cutoff, if `automation/state` has no acknowledged `packet.status:"ready"` for that exact edition, create/reuse `automation/editorial/<edition-id>` from current `main` and commit only missing exact schema-v1 `automation/wake/<edition-id>.json` with `packet_missing_at_handoff`. Then stop the current invocation. A later invocation may consume the acknowledged packet; never wait for or poll Actions inside the wake invocation. Do not wake ready/in-flight/published work.
5. Only when no Canonical decision and no current missing-packet wake is required may the task continue to one English repair.

## 2. Canonical submission
- Both Chinese and English headlines and archive titles must name their game, company or person so they remain understandable without the separate subject label.
- Return exactly one `include`, `exclude`, or `needs_review` for every packet package/tracking item; add nothing outside the packet. Use only opened evidence. `official` requires opened primary evidence; `multi_source_verified` requires two independent reliable sources. Never invent a `requires_subject_identity` subject.
- Daily uses `upcomingMode:"inherit_and_patch"`. Do not copy `editorialInput.upcomingBaseline.items` or replace the calendar with empty data. Trusted publisher carries the newest verified Canonical calendar forward and expires entries outside the strict future-15-day window.
- `editorialInput.upcomingBaseline.refreshRange` permits calendar-only research across the full future-15-day window daily. Use `upcomingDiscovery` as leads, prioritize known/missing/cross-source titles, and open official developer/publisher or platform pages before adoption. Check PC/PlayStation/Xbox/Nintendo gaps, delays and date/platform/region conflicts; record limitations in sourceReport. Never modify news decisions or delete entries because discovery failed. Submit only changed calendar items with HTTPS sources.
- Follow live `AGENTS.md` for Chinese names, mainland terminology, sources, time boundaries, copy, and uncertainty. Narrow naming lookups cannot change facts. Every include needs a complete language-neutral `sharedFactFrame`; do not invent issue numbers, final IDs, or digests.
- Before committing, self-check every include against the immutable packet. `sharedFactFrame.subjectTitleKey` and `sharedFactFrame.platforms` must exactly match the Canonical title/platform decision; source/time/fact status stays evidence-bounded. If durable `validationErrors` name a field, repair that field without changing unrelated decisions or adding evidence.
- For every normal Daily submission, attempt complete `locales.en` by default. English is nonblocking, but omission is exceptional. English matches Canonical order and the same facts. `locales.en.upcoming` covers only submitted calendar patches; inherited items need not repeat. If complete English is unsafe, omit `locales.en`.
- Commit only `automation/inbox/<edition-id>.json` on `automation/editorial/<edition-id>`. After it succeeds, do not poll Actions and stop.

## 3. One English repair
Choose the oldest published Daily from `2026-08-31-daily` onward whose English is unavailable for `editorial-overlay-missing` or `editorial-overlay-invalid`. Final Canonical `entryId` and order are authoritative. Each English entry uses final Canonical `entryId` and covers Canonical once in order. Restate only Canonical/accepted evidence; do not rediscover news or alter facts. Commit only schema-v1 `locale:"en"` to `automation/locale-inbox/<edition-id>.json` on `automation/locale/en/<edition-id>`. Trusted publisher hash-guards archive/latest/manifest and updates only English state/Overlay. Then stop.

Do not inspect or poll Actions, create/delete workflows, edit `automation/state`, publish Canonical directly, advance editions, or create/disable/rename/reschedule any long-lived task. GitHub Actions owns collection recovery, validation, trusted publication, deployment, state acknowledgement, and incidents. A single Canonical or locale failure must never mutate the active Daily task.
